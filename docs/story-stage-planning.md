# 阶段任务与依赖更新 v0.3

入口仍为 `/?view=story-generator`。本版继续使用 JSON 规则包，新增阶段任务图、候选路线计算和受影响反应调度。

## 当前行为

主线由基础包声明四个阶段：取得线索、准备物资、抵达目标、完成目标。`resolve`需要线索、物资与targetReached；旧工坊由travel设置抵达，新Demo由实际坐标事实设置。角色的本局最终目标不随状态更新改变。

阶段是带前置关系的有向无环图，可以声明分支和汇合。当前阶段取声明顺序中第一个未满足完成条件且前置条件已满足的阶段。路线从真实可用行动中筛选，不替代行动自身的条件验证。

- 支持提前搜集物资；推荐阶段不强制限制其他合法行动。
- 知情者死亡或离开会移除对应信息路线。普通人物不能被误认为知情者。
- 丢失物资后，已经完成的准备阶段显示“条件需恢复”，保留首次完成时间与日志。
- 地点封闭后，抵达/完成行动失效；恢复通行后继续推进。
- 已取得的线索、既存笔记和剩余知情者保留，各自依条件提供路径。
- 所有主线线索永久失去时，基础规则结束主线；未完成阶段关闭。
- 已完成的任务与终局不重新打开，完成记录不因之后资源变化而消失。
- 卸载带计划的扩展包会归档计划并撤销其路线；重新加载同ID阶段时保留首次完成时间。

2026-10-14接入真实地图移动：运行器移动到goal锚点时，生命周期提交player-location事实并更新targetReached；离开该点会撤销当前抵达条件，历史完成记录保留。旧工坊仍允许抽象travel，新Demo过滤此选项。阶段图里的候选travel仍是旧规则描述，尚未改成通用空间行动路线；新Demo以合法世界移动为实际执行途径。

## 规则包扩展

`RulePack.plans` 为可选字段，旧的行动/反应包仍兼容。例如：

```json
{
  "id": "journey",
  "title": "通向{goal}的旅程",
  "questId": "main",
  "stages": [
    {
      "id": "learn",
      "title": "取得线索",
      "requires": [],
      "complete": {"op": "eq", "left": {"ref": "clue"}, "right": true},
      "routes": [
        {
          "id": "notes",
          "title": "研究既存笔记",
          "when": {"op": "eq", "left": {"ref": "notes"}, "right": true},
          "actionIds": ["notes"]
        }
      ]
    }
  ]
}
```

`questId` 当前支持已有 `main` / `side` 任务。`requires` 引用同一计划中的阶段ID，注册时检查重复、缺失前置和循环。每包最多16个计划，每计划最多16个阶段，每阶段最多16条路线。

`routes.when` 判断世界条件，`routes.actionIds` 绑定行动规则。NPC路线可增加 `npcWhen`，按实际行动目标筛选人物，避免“场上有普通NPC”被当作“可向知情者取得线索”。行动数据新增 `actionId`、`npcId`、`questId`，不再从展示编号猜测对象。

路线引用的行动必须已存在；跨包引用必须声明直接 `requires`，因此不能卸载被计划依赖的行动包。替换规则包时，也检查其他计划的行动引用。

## 阶段状态与事实

| 状态 | 含义 |
|---|---|
| locked | 前置阶段的当前条件未满足 |
| ready | 当前存在可执行的候选路线 |
| blocked | 当前没有可执行路线，可能等待外部条件变化 |
| completed | 当前完成条件满足 |
| invalidated | 曾完成过，但当前必要条件失效 |
| closed | 所属任务结束，阶段不再推进 |

`completedAt` 记录首次完成时间；恢复条件不重复生成首次完成事件。当前满足条件与过去完成事实分别保存。

候选路线代表可执行的尝试，不保证概率行动一定成功。旧任务失败、放弃和过期仍由规则包定义；暂时无法接触知情者不会自动被判定为主线永久失败。

## 依赖调度

代码职责：

| 文件 | 职责 |
|---|---|
| `dependency-keys.ts` | 将字段引用映射为世界/人物/任务的规范键 |
| `dependencies.ts` | 提取条件、效果和模板中的引用，计算受支持字段变化 |
| `scheduler.ts` | 按规则版本与实体集合编译反向索引，调度受影响反应 |
| `planner.ts` | 按阶段和路线条件计算计划状态，跳过不相关计划 |
| `engine.ts` | 统一在事务中执行反应调度、阶段更新和结果提交 |

以 `npc-0` 的信任为例，变化键是 `npc.npc-0.trust`，并同时产生集合键 `npc.*.trust`。本人物作用域的反应只监听自身键；`some` / `each` 中的集合引用监听通配键和实体集合变化。

处理流程：

1. 在工作副本应用实际行动或外部变化。
2. 比较已登记字段，取得最初变化集合。
3. 用反向索引取得候选反应，按优先级处理。
4. 效果写入新的字段时，继续唤起相关下游反应。
5. 每个反应/对象每事务最多执行一次，预算仍限制执行量。
6. 只重算依赖变化字段的计划；依据路线的真实可用行动更新推荐。
7. 验证终局保护等约束，成功后提交整个世界。

没有条件引用的反应每事务检查一次。装卸/替换规则包以及重新开局强制完整同步。其他反应依据条件和效果读取的字段变化触发；这与v0.2每次扫描全部规则的触发方式不同。持续为真的规则若需要只执行一次，仍应在规则中声明明确的状态守卫。

依赖索引按注册表版本及人物/任务ID集合缓存；卸载或替换后自动重编译。世界差异比较仍扫描已登记字段，选项仍按实时条件生成；本版没有把全部世界更新都改成局部缓存。

`World.lastUpdate` 提供本轮变化字段、求值反应、触发反应和重算计划列表，用于测试与诊断，不参与剧情。

## 外部变化接口

新增：

```ts
receiveWorldChange(world, resultId, {
  kind: 'npc-move',
  npcId: 'npc-2',
  location: '远处营地'
}, registry);
```

其他死亡、时间、通行、物资、笔记入口保留。新增player-location(区域名称、atTarget)与player-defeat，供生命周期根据运行器结果确认。外部模块仍须通过公开入口报告状态变化，不直接修改应用层的世界引用。

## 人物接口接入

依照项目 AGENTS.md，故事初始化先确定NPC姓名、职业、性格与动机，再调用人物领域公开的 generateCharacterWithParams 补齐年龄、性别、偏好与外观，完整资料保存在 NPC.profile。同局内不重抽资料。旧工坊管理抽象位置和存活；新Demo由运行器管理坐标与HP，生命周期把确认的存活投影回故事，信任和叙事地点仍由故事侧维护。人物种子使用世界种子的稳定哈希与NPC序号，保证本局内不同人物具有不同种子；不作为跨世界全局编号服务。当前页面继续展示故事所需的姓名、职业和性格，完整资料由查询接口提供。
